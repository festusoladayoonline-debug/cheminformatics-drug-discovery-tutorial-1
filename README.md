Overview
This repository contains a fully annotated, reproducible Jupyter notebook that walks through the standard early-stage triage of a small molecule library (28 compounds spanning antibiotics, antivirals, kinase inhibitors, protease inhibitors, CNS/cardiovascular drugs, and synthetic decoys) using RDKit and a handful of common Python data-science packages.
The notebook is deliberately scoped as a single, self-contained entry point: it is intended as the first of a planned multi-part tutorial series that will go progressively deeper into individual topics (fingerprint comparison across bit types, dimensionality reduction with t-SNE/UMAP, a simple ML bioactivity classifier, and a head-to-head comparison against an AI-only analysis of the same dataset). Readers who want a deeper, ADMET-focused treatment of a single target class should also see our companion tutorial, "ADMET Property Prediction and Toxicity Profiling of CDK2 Inhibitors" (Tutorial 4 in this series), which builds directly on the concepts introduced here.
The notebook is designed for:
Students and early-career researchers learning cheminformatics and Python
Medicinal chemists who want a quick, code-first refresher on descriptor/filter/similarity workflows
Instructors looking for a single-lecture-length, fully runnable teaching notebook
Anyone comparing a "by-hand" RDKit pipeline against what an AI assistant can produce unsupervised

Installation
Do not mix conda and pip in the same environment. Pick one route below and follow it exactly once.
Option A — Conda (recommended for most users)
```bash
conda env create -f environment.yml
conda activate cheminformatics\_drug\_discovery
python -m ipykernel install --user --name cheminformatics\_drug\_discovery --display-name "Python (cheminformatics\_drug\_discovery)"
```
Option B — pip + virtual environment
If you don't already use conda, a plain Python virtual environment works just as well — but you must use a Python version RDKit and NumPy already have prebuilt installers for. As of this writing, that means Python 3.9–3.11. Newer Python versions installed alongside older ones on the same machine (very common on Windows, where `python`/`py` may default to whatever was installed most recently) are the single most common cause of pip installation failures for this tutorial — see the Troubleshooting section below if this happens to you.
Step 1 — check which Python versions you have and pick one in range:
macOS/Linux:
```bash
python3 --version
```
Windows (the `py` launcher lists every version installed):
```bash
py -0
```
Look for a `3.9`, `3.10`, or `3.11` entry. If none is listed, install Python 3.11 from python.org before continuing — do not use the newest available version.
Step 2 — create and activate the environment with that specific version:
macOS/Linux:
```bash
python3.11 -m venv .venv        # replace 3.11 with whichever in-range version you found
source .venv/bin/activate
```
Windows:
```bat
py -3.11 -m venv .venv
.venv\\Scripts\\activate.bat
```
Step 3 — install and register the kernel:
```bash
pip install -r requirements.txt
python -m ipykernel install --user --name cheminformatics\_drug\_discovery --display-name "Python (cheminformatics\_drug\_discovery)"
```
Watch the end of the `pip install` output carefully — it should end with a line like `Successfully installed ...` and no line beginning with `ERROR:`. If you see any `ERROR:` line, stop and check the Troubleshooting section below before proceeding; the kernel registration step can succeed even if the actual package install silently failed, which will only surface later as `ModuleNotFoundError: No module named 'pandas'` when you try to run the notebook.
> \*\*New to virtual environments?\*\* A virtual environment (venv) or conda environment is an isolated copy of Python with its own packages, so this tutorial's dependencies never conflict with anything else on your machine. You create one once, `activate` it every time you work on the tutorial, and `deactivate` it when you're done. Conda additionally manages non-Python dependencies (like RDKit's compiled C++ core), which is why it's the more common choice for cheminformatics specifically — but either route works for this notebook.
Verify installation
```bash
python -c "from rdkit import Chem, rdBase; print('rdkit:', rdBase.rdkitVersion)"
```
> \*\*Why `numpy<2.0`?\*\* RDKit conda-forge/PyPI builds for this Python version are compiled against NumPy 1.x. Installing `numpy>=2.0` causes an `AttributeError: \_ARRAY\_API not found` crash at RDKit import. The pinned constraint in both `environment.yml` and `requirements.txt` avoids this automatically.

Running the Notebook
```bash
jupyter notebook
```
This opens a browser tab. Open `cheminformatics\_drug\_discovery.ipynb`.
Before running anything, explicitly select the correct kernel: go to Kernel → Change Kernel in the menu bar and choose the one you registered above (e.g. `Python (cheminformatics\_drug\_discovery)`). Do not assume the notebook opened with the right kernel already selected — Jupyter sometimes defaults to a base/system kernel, especially if you have multiple Python installations, and running against the wrong kernel is the single most common source of `ModuleNotFoundError` even when installation itself succeeded.
Run Cell 0 first — it only validates that your environment is set up correctly (it does not install anything). If Cell 0 reports any package as missing, stop there and fix your environment before continuing. Then run the remaining cells sequentially, top to bottom — later cells depend on dataframes and variables created earlier, so skipping around will cause `NameError`s.

Troubleshooting
These are real issues encountered while testing this tutorial, in the order you're likely to hit them. Windows, macOS, and Linux are covered separately where the fix differs. If something goes wrong, check here before asking for help.
1. `pip install` fails while building numpy, mentioning "Meson", a missing compiler, or a build error
Cause: Your default Python interpreter is a very new version (3.13/3.14+) for which `numpy==1.26.4` has no prebuilt installer, so pip tries to compile it from source — which needs a working C compiler toolchain most machines don't have set up.
Fix — check your available versions first, then rebuild the virtual environment on Python 3.9, 3.10, or 3.11 specifically:
Windows:
```bat
py -0
deactivate
rmdir /s /q .venv
py -3.11 -m venv .venv          :: use whichever in-range version "py -0" showed you
.venv\\Scripts\\activate.bat
pip install -r requirements.txt
```
macOS:
```bash
ls /usr/bin/python3\* /usr/local/bin/python3\* /opt/homebrew/bin/python3\* 2>/dev/null
deactivate
rm -rf .venv
python3.11 -m venv .venv        # if not found, install via: brew install python@3.11
source .venv/bin/activate
pip install -r requirements.txt
```
Linux (Ubuntu/Debian example):
```bash
python3 --version
deactivate
rm -rf .venv
sudo apt install python3.11 python3.11-venv     # if 3.11 isn't already installed
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```
If no 3.9–3.11 version is available anywhere on your system, install Python 3.11 from python.org (Windows/macOS) or via your distribution's package manager (Linux) before continuing — do not use the newest available version.
2. Windows only — `pip install` fails partway through with `OSError: \[Errno 2] No such file or directory`, mentioning a very long file path, or a hint about "Windows Long Path support"
(macOS and Linux do not have this limitation and can skip this section entirely.)
Cause: Windows has a default 260-character limit on full file paths. Combined with a long project folder name and the deeply-nested files some packages install (this shows up most often with JupyterLab's widget extension), the full path can exceed that limit and the install silently fails partway through — even though the terminal output looks mostly successful.
Fix — enable Windows long path support (one-time, requires a restart):
Press `Win + R`, type `gpedit.msc`, press Enter. (Windows Home doesn't have this — use the registry method below instead.)
Go to Computer Configuration → Administrative Templates → System → Filesystem
Double-click "Enable Win32 long paths", set it to Enabled, click OK
Restart your computer (required)
If `gpedit.msc` isn't available (Windows Home edition):
Press `Win + R`, type `regedit`, press Enter
Navigate to `HKEY\_LOCAL\_MACHINE\\SYSTEM\\CurrentControlSet\\Control\\FileSystem`
Find or create a DWORD (32-bit) value named `LongPathsEnabled`, set it to `1`
Restart your computer
Faster alternative if you can't restart right now: move (or re-clone) the project into a much shorter path, e.g. `C:\\cdd\\` instead of `C:\\Users\\...\\Desktop\\My Research\\Tutorial Manuscripts\\...\\Revision\_Files\\`, and rebuild the virtual environment there. Shortening the path avoids the 260-character limit entirely without touching Windows settings.
After either fix, delete and rebuild the virtual environment from scratch (don't just re-run `pip install` on top of a partially-installed one).
3. Linux only — `pip install` fails immediately with `error: externally-managed-environment`
Cause: Recent Debian/Ubuntu releases (Debian 12+, Ubuntu 23.04+) block `pip install` outside a virtual environment by default (PEP 668), to protect the system Python.
Fix: This is exactly what a virtual environment solves — as long as you've activated `.venv` first (prompt should show `(.venv)` at the start), `pip install -r requirements.txt` will work normally inside it. If you're seeing this error, double check you actually ran `source .venv/bin/activate` in the same terminal session before installing. Do not work around this with `--break-system-packages`; use the venv as intended instead.
4. macOS only — Apple Silicon (M1/M2/M3) architecture mismatch
Cause: Very rarely, an older/cached wheel built for Intel Macs gets picked up on Apple Silicon, causing an `ImportError` at runtime even though installation reported success.
Fix: Confirm your Python itself is a native ARM64 build (`python3 -c "import platform; print(platform.machine())"` should print `arm64`, not `x86\_64`), then rebuild the venv from scratch with `pip install --no-cache-dir -r requirements.txt` to force fresh downloads instead of any cached Intel wheels.
5. `ModuleNotFoundError: No module named 'pandas'` (or rdkit, numpy, etc.) when running the notebook, even though `pip install` seemed to work
(This applies on every OS.)
Cause 1 — install actually failed silently. Scroll back up through your `pip install -r requirements.txt` output and look for a line starting with `ERROR:`. If a large "Installing collected packages: ..." list appeared but was followed by an error, the install did not actually complete — see issues #1–#3 above depending on your OS.
Cause 2 — wrong kernel selected. Even with a successful install, Jupyter may be running the notebook on a different Python kernel than the one where you installed the packages. In the notebook, check Kernel → Change Kernel and make sure the kernel name you registered with `ipykernel install` (e.g. `Python (cheminformatics\_drug\_discovery)`) is the one selected — not "Python 3 (ipykernel)" or any other default. This applies identically on Windows, macOS, and Linux.
6. General advice (all platforms)
Run `python -m ipykernel install --user --name ... --display-name ...` again anytime you rebuild the virtual environment — the kernel registration doesn't update itself automatically.
If you're not sure whether a previous install partially succeeded, it's almost always faster to delete `.venv` entirely and start clean than to debug a half-installed environment.
When asking for help, always include (a) your OS and Python version (`python --version` or `python3 --version`), (b) the complete output of `pip install -r requirements.txt` including the final lines, and (c) which kernel was selected in the notebook when the error occurred.

Key Features
Single-command reproducible environment — `conda env create -f environment.yml` or `pip install -r requirements.txt`
Conda and pip kept strictly separate — no mixed-manager installs, matching good-practice guidance from reviewers of our earlier tutorials
Jupyter listed as an explicit dependency in both environment files (previously only implied)
All imports centralized in Cell 1 — no scattered imports

Applicability & Scope Notes
This tutorial uses a curated 28-compound set, not a large, unfiltered vendor library — it is meant to teach the mechanics of each step, not to simulate a full-scale primary screening campaign. Attrition rates you see here (Ro5/Veber/lead-like pass rates) will typically be far more aggressive on a real, less-curated library.
PAINS alerts are AlphaScreen-derived statistical enrichment patterns, not a universal chemical law — treat a PAINS hit as a prompt for closer scrutiny, not an automatic disqualification (see Cell 9 discussion, and Capuzzi et al. 2017, J. Chem. Inf. Model.).
Tanimoto similarity thresholds are fingerprint-dependent — the "0.40 / 0.85" guideline values shown in Cell 8 are commonly cited defaults for Morgan/ECFP-type fingerprints specifically, not a universal constant; a different fingerprint (MACCS, topological, pharmacophore) can shift what counts as "similar" substantially.
